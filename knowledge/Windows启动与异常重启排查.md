# Windows 启动与异常重启排查

建立日期：2026-10-10。面向所有使用 AgentKit 的 agent；适用于 Windows 启动缓慢、登录卡顿、睡眠恢复异常和非正常重启。

这份知识保存排查方法，不保存这台电脑的当前配置。具体设备、版本、事件与处理结果见 [开机与性能诊断任务档案](../tasks/开机与性能诊断/README.md)。历史记录不代替操作前复查；阅读本文不构成更新驱动、修改服务或重启的授权。

## 先找到用户感受到的阶段

用户说“开机慢”，可能是固件阶段停留、Windows 转圈、登录处理，也可能是桌面出现后程序迟迟不能用。它们发生在不同路径，不能用一条服务错误解释所有阶段。

先问一个最有区分力的问题：慢发生在厂商标志、Windows 转圈/登录，还是桌面出现之后？涉及重启时，另确认是用户强制关机、系统自行重启，还是正常重启。优先复用任务中的证据，围绕对应时间窗口读取，避免一开始就全机扫描。

启动慢和异常重启可以同时出现，但应分别建立证据链。只有时间关联或共同日志，不足以将它们归为同一原因。

## 把日志当作观察，而不是原因

事件能证明“发生了什么记录”，通常不能单独证明“为什么”。分析时依次写出：原始字段、能够支持的结论、仍然缺少的验证。

| 观察 | 可以支持什么 | 不能直接推出什么 |
|---|---|---|
| Kernel-Power 41、EventLog 6008 | 上次没有正常完成关机 | 电源损坏、某驱动导致崩溃、用户一定强制重启 |
| BugcheckCode=0 | 此事件没有保存蓝屏错误码 | 没有蓝屏；系统可能未能写入错误码或转储 |
| LongPowerButtonPressDetected=false 或 PowerButtonTimestamp=0 | 未记录相应按键信息 | 排除用户强制关机或断电 |
| EventLog 6013 的秒数 | 记录时报告的系统运行时长 | 完整启动耗时、桌面已可用、开机不慢 |
| 一段时间没有可见事件 | 所查日志中存在记录空白 | 整段时间系统卡死；还应考虑空闲、筛选范围和采集缺失 |
| 信息级事件包含 dump/telemetry | 存在相应诊断或遥测记录 | 驱动崩溃；需核对事件级别、重复模式与真实错误 |
| 服务启动超时 30 秒 | 此次服务连接等待达到超时 | 整体启动必然延长 30 秒；还需确认发生阶段、依赖与并行关系 |
| 启动应用数量多 | 有较多启动活动候选 | 数量本身就是瓶颈；需要耗时与资源证据 |
| 驱动启动时加载警告 | 当时加载尝试失败 | 设备持续不可用；检查重试、后续事件与当前设备状态 |
| 存储 HealthStatus=Healthy | 存储子系统报告的状态正常 | 完整硬件体检通过，或排除间歇 I/O 故障 |

同样的可疑事件如果在多次没有故障的运行中也出现，应降低它对本次故障的解释力。没有查到事件时，写清日志、提供者、时间范围与权限；不能笼统宣布“没有错误”。

## 用启动性能数据区分阶段

优先读取 `Microsoft-Windows-Diagnostics-Performance/Operational` 的事件 100 与相关退化事件（例如应用事件 101），保留 XML 字段，不只看本地化摘要。

- `BootTime`：该日志报告的总体启动指标，不包含所有按电源前后阶段，也不等于全程无法使用。
- `MainPathBootTime`：主要启动路径指标；结合登录和桌面相关事件解释，避免混同固件等待或用户输入时间。
- `BootPostBootTime`：启动后活动到满足空闲判断的阶段。桌面可以已经显示，后台仍在启动；耗时长不必然意味着界面一直卡住。
- `UserLogonWaitDuration`：单独保留，不直接解释成系统故障阻塞。用户输入、自动登录等条件会影响对照。
- 应用的 `TotalTime`/退化时间：应用启动性能线索，不是该进程持续占满 CPU 的证明，也不一定处在阻塞桌面的关键路径。

程序和服务会并行启动，各项耗时不能相加。日志记录时间也可能晚于被测活动：用 XML 中的启动时间、实例标识等将退化事件关联到对应启动，不能拿事件写入时刻充当应用启动时刻。

至少对比最近几次启动，同时注明正常/异常关机、完整启动/快速启动、是否安装更新，以及用户何时登录。`IsDegradation=false` 只是日志的比较结果，不代表用户体验一定良好。若用户描述与指标不符，先核对是否为同一次启动、计时范围是否一致，再考虑启动跟踪。

## 异常重启先看之前发生了什么

事件 41 在下一次启动时记录结果。只查看重启后的告警，会遗漏重启前的真正线索。

按故障窗口查看资源耗尽 2004、相关存储错误、WHEA、显示故障、BugCheck/Windows Error Reporting、volmgr，以及可访问的转储文件。保留事件原文与 XML，避免仅凭数字 ID 判断：不同提供者可能使用相同 ID。

资源耗尽事件应同时记录系统提交量、提交上限、首位进程与占用量。提交内存不是物理驻留内存；接近提交上限意味着新的内存申请可能失败。某程序排名第一是重要线索，但仍需观察重复模式，不能直接判定内存泄漏或整机崩溃原因。不同日期的故障不得未经核验强行归因一致。

睡眠恢复附近检查系统时间调整事件。时钟跳变后，跨事件直接相减可能失真；结合事件记录顺序、XML 时间与恢复记录，而不是拼出看似精确的故事。固件恢复耗时正常也不能排除其他恢复阶段问题。

## 权限缺口要补采，不要猜

当前进程不是管理员时，启动性能日志与转储目录可能拒绝访问。查询返回空、无匹配或“日志不存在”时，先排查是否有同时出现的权限错误。

需要提权时说明用途，使用只读采集脚本；只读取相关日志、配置与目录清单，并把输出写入指定位置。不因采集需要顺手改日志配置、ACL、服务或驱动。转储内容可能含敏感数据，应先列清单，确需分析时再读取。

可复用的本机脚本：`D:/AgentKit/tasks/开机与性能诊断/原始采集/补采启动诊断.ps1`。它目前采集从 **2026-10-05** 起、最多 100 条所选启动性能事件，以及转储目录清单。以后使用前先检查日期、事件范围、路径、PowerShell 版本和权限条件；它是本机案例脚本，不是适用于所有场景的通用完整采集器。

## 用一次一个变量的对照验证处理思路

证据指向启动负载时，先选一个非必需应用关闭自启动，记录原设置和恢复方法。下一次启动对比用户体验与同口径指标；若结果受更新、登录等待等影响，就注明无法作有效对照。不必为了验证重复重启多次。

不要因为列表里有多个入口就断言启动了重复实例；也不要为优化速度同时关闭代理、安全软件和多项虚拟机服务。涉及日常依赖时先对齐范围；改动虚拟机服务后必须实际验证虚拟机网络、USB 等所需功能。

驱动更新应先确认机型、设备、驱动包版本与驱动文件版本，二者可能不同；通过官方渠道获取并保留回退方法。网卡存在错误可以支持稳定性维护，不能自动支持它是开机慢的原因。

交接时分别记录“采集完成”“设置已修改”“用户确认”“故障改善已验证”。本轮排查完成不等于根因确定；用户禁用自启动不等于提速已经验证。待办处理遵循共享 `TODO.md`，任务档案不另建执行队列。
